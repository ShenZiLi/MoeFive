## 1. 结论（TL;DR）

### 推荐方案 —— ✅ 已拍板采纳（2026-09-20）

> **Godot 4.7.2 stable + GDScript + Compatibility 渲染器**，统一六端。

**决策结果**：D1 / D1a / D1b / D1c / D1d **全部按推荐通过**；并明确 **MoeFive 不复用 MoeChess 的技术与资产**。
后者的影响：本文档 §3 矩阵与 §4.5 风险表中"复用红利"相关项**据此作废**，但**不改变裁决** —— Godot 的胜势来自原生动效/音频管线与六端一致性，**不依赖复用**（论证已在 §3 重算）。

### 必须一并接受的三条硬约束

| ID | 约束 | 原因 | 影响面 |
|---|---|---|---|
| **R1** | **必须用 GDScript，不能用 C#** | 截至 2026-09，Godot 的 C#（.NET）项目**无法通过官方途径导出 Web**；4.7 文档明确此限制，4.8 开发快照亦未加入 | 锁死主力语言，M1 起生效 |
| **R2** | **iOS 打包必须有 macOS + Xcode** | Windows 上无法产出 iOS 包 | M4 需联动 Slay.No1 宿主（MacBook Air M5） |
| **R3** | **统一用 Compatibility 渲染器** | Godot 的 Web 导出只支持 Compatibility（WebGL2），不支持 Forward+/Mobile、WebGPU | 美术定版必须**以 Compatibility 表现为基准**，见 §4.4 |

三条之中 **R1 和 R3 是"选定即锁死"的**，R2 是流程约束（可协调，但要知道它存在）。

## 2. 从需求反推技术需求

先把"这个项目到底需要什么"列清楚，再看候选方案谁满足得更好。

| 需求侧事实 | 反推出的技术要求 | 权重 |
|---|---|---|
| §8.1 六端覆盖（Win/macOS/Linux/Android/iOS/Web） | 一套代码多端导出能力 | **高** |
| §1、§4–6 **重心在 UI / 动效 / 音效** | 动画曲线、粒子、音频总线管线要成熟且易调 | **最高** |
| §9 **完全离线**、无账号、无联网 | 需要后端/云服务的方案一律排除 | 高（反向排除） |
| §3.2 15×15 棋盘、回合制、无实时物理 | 逻辑算力需求极低，**不需要强计算引擎** | 低 |
| §6 音效变体、音量总线分离 | 多总线混音 + 运行时音量控制 | 中 |
| §5.3 同屏 ≤12 个 Tween、≤60 粒子 | 2D 动画系统需支持并发 Tween 与曲线编辑 | 中 |
| 面向休闲用户，"前 3 秒留住人" | 启动要快、首屏要好看 | 中（但**与 Web 端体积直接冲突**） |
| Moe 系列已有前作（MoeChess） | 资产管线 / 美术规范 / 动效模式可否复用 | **高** |

**一句话总结**：这是一个**逻辑极轻、表现极重**的 2D 项目。技术选型的天平应该压在**动画与音频管线的成熟度和多端一致性**上，而不是运行时性能。

## 3. 候选方案对比

### 候选清单

| 代号 | 方案 | 说明 |
|---|---|---|
| **A** | Godot 4.7.2 + GDScript | 开源引擎，2D 专用渲染器，与 MoeChess 同源 |
| **B** | 纯前端 Web（TypeScript + PixiJS / Phaser） | 浏览器原生，套壳（Tauri / Capacitor）出桌面与移动 |
| C | Godot 4.7.2 + C# | 语言更熟，但 **Web 端不可用 → 直接出局**，仅列出说明原因 |
| D | Cocos Creator 3.x | 国内生态强，但 2D 表现力与 Moe 系列既有管线不匹配 |

### 对比矩阵

| 维度 | A. Godot + GDScript | B. 前端 Web + 套壳 | D. Cocos Creator |
|---|---|---|---|
| 六端覆盖 | ✅ 官方导出模板，六端一等公民 | ⚠️ Web 原生；桌面/移动靠套壳，iOS 壳层体验需调 | ✅ 支持 |
| **动效能力**（本项目核心） | ✅✅ Tween / AnimationPlayer / 曲线编辑器 / GPUParticles2D，**弹性与 squash 类手感是引擎原生能力** | ⚠️ 需自建动画系统（GSAP 等），粒子与曲线调优成本高 | ✅ 有动画编辑器 |
| **音频管线**（本项目核心） | ✅✅ AudioServer 多总线、`.ogg` 流式、运行时变调（做音效变体很直接） | ⚠️ WebAudio 需手写总线与变体逻辑 | ✅ 有 |
| Web 首包体积 | ⚠️ 空引擎 ~24MB 未压 / **~9MB gzip**，含资产实测可达 20–37MB | ✅✅ 可压到 < 3MB | ⚠️ 中等 |
| Web 端兼容性 | ⚠️ 仅 WebGL2；**Safari / iOS 浏览器有问题**；多线程需 COOP/COEP 头 | ✅✅ 浏览器原生，无短板 | ⚠️ 一般 |
| 与 MoeChess 复用 | ~~同引擎、同资产与动效管线~~ → **已明确不复用，该行作废** | ❌ 全部重做 | ⚠️ 部分概念可迁 |
| 授权成本 | ✅ MIT，零费用零分成 | ✅ 开源库均为宽松许可 | ⚠️ 需核对当前授权条款 |
| 上手成本 | ✅ 用户已有 Godot 经验（MoeChess） | ⚠️ 需搭一套工程化（构建/热更/套壳） | ⚠️ 需另学 |
| **本机就绪度** | ⚠️ 引擎未安装（其余依赖已就位，见 §5） | ✅ Node 22 已就位 | ⚠️ 未安装 |
| 离线 / 隐私 | ✅ 全离线 | ✅ 全离线 | ✅ |

### 关于候选 C（Godot + C#）—— 为什么直接出局

C# 在桌面/移动端可用，但**无法导出 Web**。而需求 §8.1 明确把 Web 列为 **P0**。这意味着选 C# 就要么放弃 Web 端，要么维护 GDScript / C# 两套代码 —— 后者对本项目的规模而言是纯粹的负担。**排除。**

### 关于候选 B —— 值得认真对待的对手

B 在**唯一弱点（体积与浏览器兼容）上是全胜的**，而体积恰好是休闲游戏"打开即玩"的命门。它输在哪里：

- 本项目 3/4 的工程量在动效与音效上。Godot 的 Tween 曲线、AnimationPlayer 关键帧、AudioServer 总线是**开箱即用的调优工具**；在 B 里这些都要自建，且很难做到引擎级的细腻度。
- 桌面与移动端要靠 Tauri / Capacitor 套壳，壳层与原生体验的缝隙需要额外处理（窗口缩放、触控延迟、音频焦点）。
- ~~MoeChess 既有的资源规范与动效模式无法复用。~~ → **此项已失效**：主体明确**不复用 MoeChess**，故 A 与 B 在该维度打平，**不构成 B 的劣势**。

**裁决（按"不复用"前提重算）**：B 依然输在**动效与音频管线必须从零自建**——而这恰好是本项目 3/4 的工程量所在。A 的胜势来自引擎原生能力，**与是否复用 MoeChess 无关**，故 D1 结论不变。

> 换言之：即便把"MoeChess 复用"这块红利从 A 这边完全拿掉，A 仍然领先 —— 这是本次拍板最需要确认的一点，已确认成立。

## 4. 推荐方案详解

### 4.1 版本锁定

| 项 | 值 | 理由 |
|---|---|---|
| 引擎 | **Godot 4.7.2 stable** | 当前稳定版（2026-08-18），4.7 系列维护中 |
| 不选 4.8 | 开发快照，非稳定 | 六端出包项目应站稳定分支 |
| 不选 4.6 | 已进入低维护阶段 | 4.7 默认启用 WASM SIMD，Web 端性能更好 |

### 4.2 语言与架构取向

- **语言：GDScript**（R1 强制）。语法接近 Python，棋类逻辑表达无障碍。
- 不引入 GDExtension / 原生库 —— 会显著抬高六端打包复杂度，且本项目无性能刚需。
- 纯 GDScript 项目**不需要 NDK 编译**，Android 打包链路大幅简化（见 §5）。

### 4.3 Web 端导出策略（针对体积与兼容的正面应对）

| 措施 | 说明 |
|---|---|
| **nothreads 导出** | 关闭 `thread_support`，规避 SharedArrayBuffer 的 COOP/COEP 头要求，**任意静态托管都能跑**。代价是失去多线程 —— 对回合制棋类**无实质影响**，是本项目最划算的一刀 |
| Brotli + 「优化大小」模板 | 用发布模板而非调试模板，配合服务器 Brotli |
| 功能裁剪 | 禁用 3D 物理、Navigation、未用音视频导入器 |
| **PCK 分包 + 异步加载** | 引擎先启动显示加载界面，美术与音频资源包异步载入 |
| 美术资源预算 | 贴图以 WebP 为主，单图 ≤1024×1024，启用 **Mipmap** |

> ⚠️ **对需求文档的回写项**：§9 现写"Web 首包 ≤ 25MB"。以 Godot 空引擎 ~9MB(gzip) 计，加资产后现实区间是 **18–28MB (gzip)**，用分包后**首屏可玩所需**可压到 ~12MB。建议 M0 拍板后把该指标改为「Web 首屏可加载 ≤ 12MB(gzip)，完整资源按需加载」。此项**未擅自改动基线**，待批。

### 4.4 渲染器决策（R3 展开）

**统一 Compatibility，桌面端也不要开 Forward+。**

理由：
- 若桌面用 Forward+、Web 用 Compatibility，同一套美术在两端的光影与混合表现会不一致 —— 对一个"侧重 UI 视觉"的项目，这是**致命的验收风险**。
- 代价：桌面端放弃 SSAO / SSR / 高质量阴影等 Forward+ 特性。但这是 **2D 项目**，Light2D、CanvasItem Shader、混合模式在 Compatibility 下支持完整，**黏土质感 2D 场景不受影响**。

**行动要求**：美术定版必须在 **Compatibility 渲染器**下比对，不得在 Forward+ 下确认美术效果后再去适配。

### 4.5 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| Web 端 Safari / iOS 浏览器兼容问题 | **中** | ① iOS 端走原生 IPA 而非浏览器（原生导出无此问题）；② Web 端明确标注推荐 Chrome / Edge，iOS 用户引导下载 App |
| Web 首包偏重，失去"点开即玩"的轻快 | 中 | §4.3 四项措施；若实测仍不可接受，降级为"Web = 试玩端"，正式端聚焦桌面 + 移动（见决策项 D1c） |
| ~~未找到 MoeChess 工程 → 同源复用的实际抓手存疑~~ | ~~中~~ **已消除** | ✅ 主体明确**不复用 MoeChess 的技术与资产**，该项不再是风险。Godot 的独立价值（六端一致性 + 原生动效/音频管线）不受影响 |
| 引擎与依赖未安装 | ~~低~~ **已消除** | ✅ Godot 4.7.2 stable 已就位（`C:\Dev\godot`），JDK 17 与 Android SDK 均在；仅导出模板待装（只影响 M2/M4 打包） |
| 单点：iOS 打包依赖 No.1 宿主 | 低 | 提前约定 Mac 侧环境（Xcode + 签名证书），避免临近发版才卡住 |
